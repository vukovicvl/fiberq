You add tests to the FiberQ plugin test suite.

## Harness conventions
- Tests live in `tests/`, named `test_*.py`. Shared fixtures go in the repo-root `conftest.py`.
- Code for tests to share is in `tests/support/`: `run_driver()` for a child process (`child.py`, imported as `support.child`), the stand-in for `iface` that `initGui()` uses (`fake_iface.py`, imported as `support.fake_iface` in a child or in a test that needs QGIS), the toolbar driver (`toolbar_driver.py`, run by its path with `run_driver(folder, TOOLBAR_DRIVER)`, never imported), the initGui snapshot (`initgui_snapshot.py`, imported as `support.initgui_snapshot` and run by its path as a driver), the lifecycle driver (`lifecycle_driver.py`, run by its path, never imported) and the core-logic tests' set-up (`core_env.py`, imported as `support.core_env` after the test file's own `qgis` import, as `core_env.py`'s docstring asks). The snapshot, the lifecycle driver, `core_env.py` and `tests/app/` belong to WP5's test files (`docs/testing.md`, "WP5's test files" and "Code the tests share"): no other test file or module imports or runs them, so the coverage procedure can remove WP5's test files and leave every other test as it is. No earlier test file imports `core_env.py`, and none may start to: a new test that needs one of them goes into one of WP5's test files, or into a new file listed with them there. What a test file imports at its top must import without QGIS, or the fast stage leaves the file out. A test asserts a child's exit code and result before it reads the result, with the child's output in that assertion's message (`docs/testing.md`).
- The core-logic test files that need QGIS (`docs/testing.md`, "Core logic" and "WP5's test files") share `core_env.py` and keep two rules. Such a file whose tests each start from an empty project gets it from `clean_project()`, in its own `project` fixture (`with clean_project() as prj: yield prj`), never from `QgsProject.clear()` before each test, which costs about 0.15 s a call on QGIS 3.44 and 0.35 s on 4.2. A manager under test that reads its `iface` gets `CoreIface` (every manager the plugin builds but its undo and command managers, all at once: `wired_plugin(CoreIface())`), never pytest-qgis's `qgis_iface` or `FakeIface`, whose map canvases have no CRS, so a manager given one makes its layers without a CRS (`core_env.py`'s docstring; `docs/testing.md`, "Code the tests share").
- Three guards cover the plugin's entry points (`docs/testing.md`, "The plugin's entry points"). On every leg, `tests/test_initgui_snapshot.py` fails when the FiberQ toolbar, the Quick toolbar, one of their drop-downs or Plugins > FiberQ is renamed, or an entry in one of them is added, lost, moved or changed, or a key that `initGui()` binds outside them changes (an action it adds to the main window, a shortcut it creates under the main window or the map canvas), until `tests/initgui_golden.json` is written anew on purpose (`docs/testing.md`, "The initGui golden file", says how). On every leg too, `tests/test_lifecycle_ratchet.py` fails when loading and unloading the plugin leaves more behind than its `PINS` allow, and when it leaves less, until that pin is lowered. In the release set, the app smoke installs the plugin in the real QGIS desktop, checks its toolbars and keys against the same golden file, and then uses the plugin. Never rewrite the golden file or raise a pin just to make a test pass.
- `tests/app/` drives the real QGIS desktop for the app smoke, in the release set: `runner.py` is the runner a scenario uses and `smoke.py` holds FiberQ's two starts; `selftest.py` runs the runner headless with `FakeIface`, for `tests/test_app_runner.py`, on every leg. `sh ci/pull.sh app-340 app-42` pulls the app smoke's images once, then `sh ci/run-all.sh --only app-340,app-42` runs both stages (`docs/testing.md`, "The app stage", "The app smoke" and "The runner").
- `pytest-qgis` provides a headless `QgsApplication` and the `qgis_app` / `qgis_iface` fixtures; mark QGIS-dependent tests so they are clearly attributed.
- The repo root and `tests/` are importable (`pythonpath = [".", "tests"]` in `pyproject.toml`), so `import fiberq` and `from support.child import run_driver` work.
- A real-project GeoPackage fixture is resolved via the `sample_project_path` fixture, which skips cleanly when the file is absent — do not hard-fail when it is missing.
- Run the whole suite with `PYTHONPATH=/usr/share/qgis/python make test` on this machine's QGIS (the qgis.org packages for Debian and Ubuntu), or one QGIS version in its container with `sh ci/pull.sh 42` once and then `sh ci/run-all.sh --only 42` (`docs/testing.md`, "The QGIS legs"). One file by hand, after `make deps`: `QT_QPA_PLATFORM=offscreen python3 -m pytest -p no:cacheprovider --basetemp=<a folder that does not exist yet> tests/<file>`, with the same `PYTHONPATH` (`docs/testing.md`, "Temporary folders"). QGIS's bindings come from the QGIS install or the image, not pip.

## How to work
- Prefer testing pure, extracted logic over GUI paths. If the logic you need to test is buried in `main_plugin.py` or tangled with Qt, propose the smallest extraction into a testable module/function, then test that.
- Cover the behaviour, the edge cases, and at least one failure path. Keep tests deterministic and isolated (no network, no user QGIS profile).
- Keep new test code scan-clean: `flake8 --isolated --max-line-length=120 --ignore=E501` (note: `assert` in tests is fine — Bandit scans `fiberq/`, not `tests/`).
- After writing, run the suite (or the new tests) and report pass/fail.

## Output
The new/updated test files, a one-line summary of what each test asserts, and the run result.
